## 1. Problem

### System

- Single chat room
- One Go server
- React client

### Rules

- User must provide a name before joining
- Name is immutable for the session
- All events are in-memory only
- No persistence, no authentication, no scaling
- Server restart clears all state

**Non-goals**

- Multi-room support
- Message history persistence across restarts
- User identity beyond session name
- Reliability across restarts

---

## 2. Behavioral guarantees

1. A user must provide a name before joining the chat
2. The server rejects WebSocket connections without a name
3. Connected users receive events emitted by the server
4. User messages include sender name, content, and timestamp
5. Empty user messages are not broadcast
6. Disconnected users stop receiving events
7. Every emitted event includes a server-generated timestamp
8. A user connection emits a system `join` event
9. A user disconnection emits a system `leave` event

All guarantees are externally observable.

---

## 3. Event model (wire contract)

All server-to-client communication uses `ChatEvent`.

```ts
type ChatEvent =
  | {
      type: "message";
      sender: string;
      content: string;
      timestamp: number; // unix milliseconds, server-generated
    }
  | {
      type: "system";
      event: "join" | "leave";
      user: string;
      timestamp: number; // unix milliseconds, server-generated
    };
```

Notes:

- Clients must not generate timestamps
- Clients may ignore unknown fields or event types
- System events are server-emitted only

## 4. Server truth (integration / boundary tests)

### Test 1 — reject anonymous connection

**Given**

- Client opens WebSocket without name

**Expect**

- Connection is rejected (close or error)

---

### Test 2 — accept named connection

**Given**

- Client opens WebSocket with name `"Alice"`

**Expect**

- Connection succeeds
- Server associates client with `"Alice"`

---

### Test 3 — broadcast message event

**Given**

- Alice and Bob are connected
- Alice sends `"Hello"`

**Expect**

- Bob receives:

```json
{
  "type": "message",
  "sender": "Alice",
  "content": "Hello",
  "timestamp": <number>
}
```

- Alice also receives the event

---

### Test 4 — reject empty message

**Given**

- Alice sends `""`

**Expect**

- No client receives any event

---

### Test 5 — disconnect cleanup

**Given**

- Alice disconnects
- Bob sends `"Hi"`

**Expect**

- Alice receives nothing
- Server remains stable

---

### Test 6 — broadcast join event

**Given**

- Alice connects with a valid name

**Expect**

- All connected clients receive:

```json
{
  "type": "system",
  "event": "join",
  "user": "Alice",
  "timestamp": <number>
}
```

---

### Test 7 — broadcast leave event

**Given**

- Alice disconnects

**Expect**

- Remaining clients receive:

```json
{
  "type": "system",
  "event": "leave",
  "user": "Alice",
  "timestamp": <number>
}
```

---

### Test 8 — timestamp integrity

**Given**

- Any event is broadcast

**Expect**

- `timestamp` exists
- Is a number
- Is generated by the server

Any implementation that passes Tests 1–8 is compliant.

## 5. Client truth (runtime executables)

### Executable 1 — name gate blocks chat

- Chat UI is not rendered before name entry
- No WebSocket exists before join

---

### Executable 2 — joining with name opens connection

- WebSocket opens with `?name=Alice`
- Chat UI renders
- Name becomes immutable

---

### Executable 3 — empty messages are not sent

- `send()` is not invoked
- No WebSocket frame is sent
- Events do not change

---

### Executable 4 — sending a message

- WebSocket sends `{ content: "Hello" }`
- Input clears immediately
- UI does not optimistically append events

---

### Executable 5 — receiving events

- Events are appended in arrival order
- Message and system events are both handled
- Sender/user, content, and timestamp are visible

---

### Executable 6 — render timestamps

- Each event displays a formatted timestamp
- UI does not generate or modify timestamps

---

### Executable 7 — render system events

- Join and leave events are visible
- System events are visually distinct
- System events are not user-sendable

---

### Executable 8 — disconnect handling

- Status becomes `closed` or `error`
- UI remains stable
- Sending is disabled

---

### Executable 9 — cleanup on unmount

- WebSocket closes exactly once
- No state updates after unmount

---

## 6. Ownership and file contracts

### Event ownership (locked)

- `use-chat-socket` owns and accumulates event history
- No other module mutates events

---

### `name-gate.tsx`

- Renders name input
- Emits `onJoin(name)`
- Does not create or reference sockets
- Guarantees no WebSocket exists while mounted

---

### `use-chat-socket.ts`

- Creates exactly one WebSocket per mount
- Accumulates events in arrival order
- Exposes read-only `events`
- Manages `status` (`connecting | open | closed | error`)
- Handles disconnect and cleanup

---

### `chat-room.tsx`

- Receives `events`, `status`, `send`
- Guards empty sends
- Clears input on successful send
- Never mutates event history

---

## 7. Architectural invariants

1. Events only grow inside `use-chat-socket`
2. No socket creation outside the hook
3. UI components do not depend on socket internals
4. Unmount closes the socket exactly once
5. All timestamps originate from the server

If any invariant breaks, at least one executable fails.
