## 1. Summary of change

- Messages are generalized into timestamped events
- The server emits system events for user join and leave
- All events include a server-generated timestamp

---

## 2. New behavioral guarantees

7. Every emitted event includes a server-generated timestamp
8. A user connection emits a system `join` event
9. A user disconnection emits a system `leave` event

All guarantees are externally observable.

---

## 3. Event model (extension to wire contract)

The wire payload is extended from `ChatMessage` to `ChatEvent`.

```ts
type ChatEvent =
  | {
      type: "message";
      sender: string;
      content: string;
      timestamp: number; // unix milliseconds, server-generated
    }
  | {
      type: "system";
      event: "join" | "leave";
      user: string;
      timestamp: number; // unix milliseconds, server-generated
    };
```

Clients compliant with `0.1.0` remain compatible if they ignore
unknown fields and system events.

## 4. Server truth (new tests only)

### Test 6 — broadcast join event

**Given**

- Alice connects with a valid name

**Expect**

- All connected clients receive a system event:

```json
{
  "type": "system",
  "event": "join",
  "user": "Alice",
  "timestamp": <number>
}
```

---

### Test 7 — broadcast leave event

**Given**

- Alice disconnects

**Expect**

- Remaining clients receive a system event:

```json
{
  "type": "system",
  "event": "leave",
  "user": "Alice",
  "timestamp": <number>
}
```

---

### Test 8 — timestamp integrity

**Given**

- Any event is broadcast

**Expect**

- `timestamp` exists
- Is a number
- Is generated by the server

---

## 5. Client truth (new executables only)

### Executable 8 — render timestamps

- Each event displays a formatted timestamp
- UI does not generate or modify timestamps

---

### Executable 9 — render system events

- Join and leave events are visible
- System events are visually distinct from user messages
- System events are not user-sendable

---

## 6. New invariant

5. All timestamps originate from the server

---

## 7. Compatibility note

- No behavior from `contract@0.1.0` is removed
- Existing clients may ignore:

  - Unknown fields
  - Events with `type: "system"`

An implementation compliant with `0.1.1` must satisfy:

- All guarantees in `snapshot@0.1`
- All additions defined in this delta
